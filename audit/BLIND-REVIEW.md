## 4. 完整发现

### F-01：接入完成门槛包含首次真实执行，形成循环（P2，文件缺陷）

**实际证据：**

- `project-template/README.md:15`：“先完成项目内接入清单再进入执行。”
- `project-template/.standards/ADOPTION.md:12`：“以一个真实任务验证 Issue → 分支 → PR → 确认卡 → 用户确认 → 合并流程。”
- `standards/ADOPTION.md:12` 同样规定该真实任务验收。
- 基线第 5.2～5.3 节区分规划与执行，第 37 节标准任务链明确包含执行和验证。

**推演复现：**首次接入的 Agent 已填好核心文件、配置远端和保护规则，准备执行首个 research Issue。它按 README 将接入清单作为进入执行的前置门槛；最后一项未完成，因而不能进入执行。然而完成该项必须执行真实任务并验证、提交 PR、取得用户确认及合并。文件未明确授权“首次接入验收任务”作为门槛例外，也未把接入拆为执行前准备与执行后的验收。

**影响：**严格遵守指引的新用户或 Agent 无法同时满足这两条要求，需自行解释或向维护者询问。熟悉项目的人通常能猜到意图，但这不能替代可直接执行的入口。它不取消 main 确认要求，也不构成权限漏洞。

**建议修复：**将 README 的门槛改为“完成执行前准备项后可进入首个受控任务；该任务按正常权限流程完成后，再标记接入验收完成”。清单明确分为“执行前准备”和“首次真实任务验收”，保留用户确认及保护要求。同步两份清单。无需新增初始化脚本或复杂流程。

**复核标准：**从未执行过任务的新仓库出发，读者能指出何时允许首次执行、何时才算接入完成，且不依赖口头解释。

### 非缺陷观察与可选改进

以下不计入 P2 缺陷数量，不作为阻断发布理由：

1. **空仓库初始化需要用户参与。**清单第 7 行已明确要求记录初始化路径和平台限制并取得确认，且不授权绕过 PR/直接 push main。尚无平台专用初始化操作示例，会增加新用户负担，但本任务不要求连接平台，基线也明确不做自动初始化。建议首次接入时留下所选平台的实际方案和批准依据；未执行不能声称已验证可行。
2. **规范维护者仍待指定。**`standards/MAINTAINER.md:3` 如实保留待指定，周度整理职责与无定时任务说明一致。应在实际启用规范仓库时指定人员/Agent 和反馈收集方式；不能把“每周职责”理解为定时自动化已配置。
3. **Issue 平台状态要实际维护。**五份 Issue 模板默认正文为 todo，但 front matter 只设置类型标签。正文第 19 行已要求状态变化时同步正文或指向平台状态，满足最小当前状态字段；默认平台 todo 标签不是自动生效。首次接入可补充维护方式或将 todo 设为默认标签，这属于适配便利性。
4. **可选模板不必全部随项目复制。**独立项目仍可按锁定规范创建 DR、反馈和交接字段；基线不要求项目复制完整 optional-templates。其缺席不构成独立使用失败。
5. **权限保护是行为规则与平台规则组合。**文件明确要求用户对当前版本确认、保存批准记录，并要求自动化身份无绕过权限。能否在所选平台准确实现，需接入测试；本地文字不能替代真实保护。
