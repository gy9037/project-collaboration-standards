# 可迁移项目协作系统规范

版本：V1.0-RC1  
状态：待独立审查  
原则：轻量、渐进、可追踪、可交接、可迁移

---

# 1. 核心原则

本规范建立一套与具体 AI、模型、电脑和执行环境解耦的项目协作体系。

核心要求：

1. 项目的规则、状态、任务、决策和交接信息必须能够被不同人员、AI 和执行环境继续读取。
2. 聊天记录不是正式事实源。
3. 不为了未来可能出现的问题提前建立复杂流程。
4. 轻量化不能以遗漏关键条件为代价。
5. 信息只在真正需要时创建和维护。
6. 自动化建立在稳定流程之后，不提前自动化尚未验证的流程。

---

# 2. 系统组成

整个体系分为三部分：

## 2.1 Idea Lab

用于保存、探索和验证尚未正式立项的想法。

## 2.2 正式项目

通过立项条件后建立独立 Git 仓库，进入正式项目生命周期。

## 2.3 全局规范体系

维护所有项目共同遵守的规则、规范版本和流程反馈。

---

# 3. Idea Lab

## 3.1 目的

任何突然产生的想法先进入 Idea Lab，而不是立即建立正式项目。

Idea Lab 负责：

- 捕获想法
- 需求探路
- 可行性验证
- 成本与风险分析
- 判断是否值得正式投入

## 3.2 状态

统一使用：

`Inbox → Exploring → Validating → Ready`

以及：

`Parked / Dropped`

含义：

- Inbox：刚记录，尚未分析
- Exploring：正在梳理问题和方向
- Validating：正在验证关键假设和可行性
- Ready：已经达到正式立项条件
- Parked：可行，但暂时不做
- Dropped：决定放弃，并保留原因

## 3.3 想法初始记录

Inbox 阶段只强制记录：

- 临时标题
- 原始想法
- 记录日期

不要求一开始填写完整分析内容。

随着探路逐步补充：

- 想解决的问题
- 使用场景或目标对象
- 预期价值
- 关键假设
- 已有证据
- 可行性
- 时间、资金、学习、维护成本
- 风险
- 外部依赖
- 机会成本
- 最小验证方案
- 退出条件
- 当前结论
- 下一步

未经验证的信息必须明确标记为：

`假设 / 待验证`

不得写成已确认事实。

## 3.4 可行性评估

主要检查：

1. 价值
2. 证据
3. 可行性
4. 成本
5. 风险
6. 外部依赖
7. 机会成本
8. 最小验证方式

同时考虑退出条件，避免因为已经投入部分成本而无限继续。

V1 不建立复杂评分系统。

## 3.5 正式立项条件

Idea 进入正式项目至少满足：

1. 问题基本明确
2. 关键可行性已经判断
3. 关键假设已经识别
4. 综合价值、成本和风险后值得投入
5. 第一阶段目标明确
6. 当前范围和暂不做的内容基本明确
7. 已经知道一个可以执行的第一步

不要求所有长期需求、架构和计划全部确定。

正式立项后，原 Idea 不删除，并记录其对应的正式项目。

---

# 4. 正式项目类型

正式项目分：

- `code`
- `non-code`
- `hybrid`

## code

主要成果是软件、脚本、服务等，需要构建、测试或部署。

## non-code

主要成果是研究、方案、设计、内容、运营或其他非软件交付物。

## hybrid

代码和非代码工作长期都占重要部分。

项目类型可以由 AI 初步判断，但必须在立项时明确记录。

不同项目使用同一核心规范，只在需要时增加类型特有内容。

---

# 5. 正式项目生命周期

正式项目从立项开始，不重复 Idea Lab 的探路过程。

生命周期：

`立项 → 规划 → 执行 ↔ 验证 → 阶段交付 → 维护 / 迭代`

另外存在：

- `Paused`
- `Archived`

## 5.1 立项

只收集足够开工的信息：

- 项目名称或临时名称
- 项目类型
- 项目目标
- 第一阶段目标
- 当前范围
- 暂不做什么
- 关键约束
- 已知风险和未验证假设
- 第一批准备推进的事项

项目名称允许后续修改。

### 最低完整性检查

进入执行前必须确认：

- 第一阶段目标可以验收
- 当前边界基本清楚
- 关键约束已经识别
- 高风险依赖已经验证或有明确验证计划
- 不存在阻止开工却无人处理的未知问题
- 第一批任务足够明确

原则：

**轻量不等于模糊。只省略当前不需要的信息，不省略会影响能否开工的信息。**

## 5.2 规划

完成：

- Issue 拆分
- 依赖判断
- 优先级判断
- 验收标准
- 风险判断
- 执行者分配
- 必要的独立审查节点

## 5.3 执行 ↔ 验证

执行和验证是循环关系。

每完成一个可验证单元就进行验证。

失败则返回执行。

发现新的独立需求时：

- 不在当前 Issue 中无限扩张
- 回到规划
- 必要时建立新的 Issue

## 5.4 阶段交付

当前阶段目标达到后：

- 完成阶段验收
- 更新 PROJECT.md
- 更新 Issue / PR
- 更新必要决策记录
- 标明已知风险和未验证内容

## 5.5 维护 / 迭代

Bug、优化、新需求重新进入：

`规划 → 执行 ↔ 验证 → 阶段交付`

## 5.6 Paused

暂时停止但未来可能继续。

暂停前必须留下足够恢复的信息。

## 5.7 Archived

项目明确结束或废弃。

保留完整历史，不再继续维护。

---

# 6. 项目核心文件

所有正式项目至少包含：

## README.md

面向人员：

- 这是什么项目
- 项目基本用途
- 如何开始了解或使用

## PROJECT.md

项目总入口和当前状态。

主要记录：

- 项目目标
- 项目类型
- 当前阶段
- 当前 1～3 个重点
- 关键约束
- Critical Areas
- 重要决策索引
- 当前重要 Issue / PR 入口
- 文档导航
- 最近更新时间

PROJECT.md 不记录流水账。

只在以下情况更新：

- 阶段变化
- 当前重点变化
- 关键约束变化
- 重要入口变化
- 关键区域变化

## AGENTS.md

定义执行规则。

至少包含：

- 当前采用的规范版本
- 项目特殊规则
- 开始任务前需要读取什么
- Issue / Branch / PR 规则
- 验证规则
- AI 权限边界
- 交接规则
- 人工确认要求
- 项目特殊约束

示例：

`Standard Version: v1.0`

项目特殊规则作为 Overrides 单独记录。

---

# 7. 分类事实源

不建立一个简单的“总优先级”。

不同信息有自己的事实源。

- 执行规则：AGENTS.md
- 项目当前状态：PROJECT.md
- 任务状态：Issue / PR
- 决策原因：Decision Record
- 实际实现：代码、测试结果、正式交付物
- 聊天记录：仅作为参考

不同事实源互相矛盾时，视为：

**信息失配**

不得简单用某个文件覆盖其他事实。

AI 应：

1. 根据证据判断是否能修正
2. 能确认则同步对应事实源
3. 无法确认则提交用户判断

---

# 8. Issue 管理

需要追踪的工作必须建立 Issue。

通常包括：

- 新功能
- Bug
- 优化
- 调研
- 维护
- 跨人员或跨 Agent 工作
- 不能一次完成的任务
- 影响正式版本或交付物的任务

极小、低风险、一次即可完成的修改允许不建立 Issue。

## 8.1 Issue 最小信息

所有正式 Issue 至少需要：

- 目标或问题
- 验收标准
- 关联对象
- 当前状态

## 8.2 按类型扩展

### Feature

补充：

- 背景
- 范围
- 暂不做什么
- 依赖

### Bug

补充：

- 现象
- 复现步骤
- 预期结果
- 实际结果
- 环境

### Improvement

补充：

- 当前问题
- 优化目标
- 约束

### Research

补充：

- 要回答的问题
- 调研范围
- 输出物
- 结束条件

### Maintenance

补充：

- 修改内容
- 风险
- 验证方式

## 8.3 状态

固定使用：

- todo
- in-progress
- blocked
- review

完成后使用平台的 Closed 状态，不额外维护 done 标签。

## 8.4 类型标签

固定基础类型：

- feature
- bug
- improvement
- research
- maintenance

其他标签按需增加，不提前建立大量分类。

---

# 9. 任务规模

AI 根据明确规则自动分类。

## 小改动

特点：

- 单点
- 低风险
- 可一次完成
- 无需独立验收
- 不涉及多人协作

可以不建立 Issue。

但仍不得直接修改 main。

## 标准任务

- 有明确目标
- 有验收标准
- 修改正式内容
- 需要追踪或可能交接

默认：

`Issue → Branch → 执行 → 验证 → PR → 合并`

## 大型任务

特点：

- 多模块
- 多人员或多 Agent
- 多个独立验收单元
- 依赖复杂
- 周期较长

处理方式：

`主 Issue / Epic → 多个子 Issue`

每个子 Issue 独立执行和验收。

不长期堆在一个巨大分支里。

判断不明确时默认按标准任务处理。

---

# 10. Git 与分支

所有正式项目必须使用 Git，并同步远端。

## main

`main` 代表当前正式、稳定、认可版本。

禁止直接向 main push。

所有修改必须通过 PR 进入 main。

## 分支

标准任务默认：

`1 个 Issue = 1 个短生命周期分支`

推荐命名：

- feature/...
- fix/...
- docs/...
- refactor/...

PR 合并后删除任务分支。

多个极小且强相关的任务可以合理共用一个分支和 PR。

---

# 11. Commit

AI 可以自行 commit，不需要逐次向用户确认。

原则：

- 一个 commit 只包含一类明确修改
- 不将无关任务混在一起
- 在有意义、已验证的小阶段及时建立恢复点
- 避免长期积累大量未提交工作

推荐类型：

- feat
- fix
- docs
- refactor
- test
- chore
- build

提交前必须检查 diff，防止误提交：

- 密钥
- Token
- 密码
- Cookie
- 日志
- 临时文件
- 无关大文件

共享分支和 main 禁止随意 force push 或改写历史。

---

# 12. PR

PR 是正式修改进入 main 的入口。

每个 PR 至少记录：

- 对应 Issue
- 实际完成内容
- 验证方法
- 验证结果
- 已知风险
- 未解决项
- 未验证内容
- 是否偏离原计划

默认使用：

**Squash Merge**

一个任务进入 main 后通常保留为一个清晰提交。

只有确实需要保留多个独立历史节点时才使用普通 Merge。

---

# 13. 用户合并确认卡

所有准备进入 main 的 PR，在最终确认前必须给用户一张简化确认信息：

- 做了什么
- 是否满足验收标准
- 验证结果
- 未验证内容
- 已知风险
- 回退方式
- AI 建议：建议合并 / 建议暂缓，并说明原因

用户只需决定：

- 合并
- 暂不合并
- 要求修改

不要求用户默认阅读代码、commit 或完整测试日志。

V1 阶段：

**所有进入 main 的修改都需要用户确认。**

---

# 14. main 保护

main 应配置保护规则：

- 禁止直接 push
- 必须通过 PR
- 已有自动检查必须通过
- 禁止强制改写历史
- 最终合并需要用户确认

临时任务分支在 PR 成功合并后可以自动删除。

其他重要分支或重要数据的删除必须确认。

---

# 15. AI 协作模型

默认采用：

**单协调者 + 多执行者**

协调者可以直接执行任务。

原则：

- 简单和标准任务可以由协调者执行
- 复杂、跨模块或高风险任务优先拆给执行者
- 关键任务增加独立审查
- 平级多 Agent 讨论主要用于方案探索

角色不绑定某个模型。

---

# 16. 模型 / Agent 路由

协调者按规则自动选择执行者，而不是依赖固定模型名称。

主要判断：

1. 任务类型
2. 复杂度
3. 能力匹配
4. 所需工具条件
5. 可用额度和成本
6. 当前任务连续性

如果偏离默认路由，需要在任务记录中简要说明原因。

V1 不固定某个模型必须负责某类任务。

---

# 17. 多 Agent 并行冲突控制

并行执行前，协调者必须检查：

- 任务之间的依赖
- 预计修改范围
- 是否会修改相同关键区域

规则：

1. 一个 Issue 同一时间只有一个主要负责人。
2. 高度重叠的任务原则上不并行开发。
3. 关键区域并发修改默认提高风险等级。
4. PR 合并前必须同步最新 main。
5. 发生冲突并处理后必须重新执行相关验证。

---

# 18. 关键区域 Critical Areas

关键区域不要求立项时全部识别。

在项目运行过程中逐步维护在 PROJECT.md。

可能包括：

## 核心功能

损坏后会导致项目主要目标无法实现的功能。

## 关键数据

丢失、错误、泄露后难以恢复，或者会影响真实业务结果的数据。

## 基础架构

被多个模块依赖、修改后会影响整体运行方式的部分。

## 核心依赖

升级、替换或损坏可能影响大量功能的重要框架或库。

## 关键配置

会影响：

- 生产环境
- 权限
- 安全
- 数据库
- 构建
- 部署

的配置。

无法确认是否属于关键区域时：

**默认按高风险处理。**

---

# 19. 独立审查

以下情况满足任意一项时应触发独立审查：

- 修改核心功能
- 影响关键数据
- 涉及账号、权限、密钥、安全、隐私
- 涉及生产环境
- 涉及数据库结构或数据迁移
- 跨多个模块且回退成本较高
- 修改基础架构、核心依赖或关键配置
- Issue 包含较高复杂度或关键不确定性
- 测试不完整或存在无法充分验证内容
- 用户明确要求二次审查

普通文档、小型样式调整、低风险小改动不强制独立审查。

审查者原则上与主要执行者不同。

主要检查：

- 是否满足验收标准
- 是否存在副作用
- 验证是否充分
- 是否遗漏风险
- 是否存在未说明的范围变化

---

# 20. AI 权限

## 默认允许直接执行

- 阅读项目
- 创建和更新 Issue
- 创建任务分支
- 修改文件
- 运行测试
- commit
- push 任务分支
- 创建 PR
- 更新项目文档
- 更新任务状态和标签

## 必须用户确认

- 合并进入 main
- 生产环境部署
- 删除重要文件、重要分支或重要数据
- 修改账号、密钥或权限
- 重大依赖升级
- 产生实际费用
- 对外正式发布或发送内容

---

# 21. 任务交接

交接信息以当前 Issue 为主。

以下情况需要写交接：

- 切换执行者
- 暂停任务
- 即将更换模型
- 额度即将达到限制
- 工作交给其他人员

交接至少说明：

- 当前进度
- 已完成内容
- 未完成内容
- 关键改动
- 风险和问题
- 下一步
- 相关 commit / PR

`docs/handoff` 只用于特殊或复杂交接，不作为日常主要记录。

---

# 22. 意外中断恢复

不能假设执行者一定有机会写最后一条交接。

因此：

- 每完成一个有意义且验证过的阶段及时 commit
- 重要恢复点及时 push 到远端任务分支
- 不长期保存大量只有本地存在的关键进度

新的执行者接手时按顺序读取：

1. PROJECT.md
2. AGENTS.md
3. 当前 Issue
4. 当前 PR
5. 相关 commit 和分支状态

不得依赖旧聊天记录才能继续项目。

---

# 23. 验证

验证方式根据项目类型变化。

## Code

可以包括：

- 测试
- 构建
- 静态检查
- 功能验证
- 部署验证

## Non-code

可以包括：

- 内容完整性检查
- 交付物核对
- 格式检查
- 数据或来源验证
- 验收条件核对

## Hybrid

根据具体交付物组合验证。

未完成验证的内容必须明确标注，不允许用“已完成”掩盖未验证状态。

---

# 24. Decision Record

只记录会影响未来判断的重要决定。

使用：

`DR-001-标题.md`

而不是记录普通日常实现细节。

每份记录：

- 状态
- 背景
- 决定
- 原因
- 影响
- 备选方案
- 日期

状态：

- Proposed
- Accepted
- Superseded
- Deprecated

旧决定被替代时：

- 不覆盖旧内容
- 新建新的 DR
- 新旧记录注明替代关系

---

# 25. 全局规范仓库

建立独立规范仓库，保存：

- 当前正式规范
- 历史规范版本
- 规范决策记录
- 流程反馈
- 规范维护者说明

规范仓库是所有正式规范版本的保存源。

项目实际执行的是：

**该项目锁定的规范版本。**

例如：

`Standard Version: v1.2`

即使中央规范已经升级到 v1.5，该项目仍按照 v1.2 执行，直到完成升级。

---

# 26. 规范升级

## 新项目

默认使用最新正式规范。

## 旧项目

默认不强制升级。

规范升级后，由规范维护者判断旧项目：

- 无需处理
- 建议升级
- 必须升级

项目升级前需要：

- 查看差异
- 判断风险
- 用户确认

不能因为全局规范变化而自动大规模修改旧项目。

---

# 27. 流程问题沉积与蒸馏

项目运行中发现流程问题时：

**先记录，不立即修改全局规范。**

每条流程反馈至少包含：

- 出现了什么问题
- 对工作造成什么影响
- 在什么场景出现
- 日期

不要求项目 AI 判断问题是否值得修改全局规范。

---

# 28. 规范维护者

规范维护者是一个角色，不绑定具体模型。

需要完整理解：

- 当前所有规范
- 规范版本
- 适用范围
- 项目例外
- 相关 Decision Record

承担三个职责：

## 规范维护

每周主动整理流程反馈。

## 规范查询

当用户询问某条规则时，准确说明当前有效规范。

## 规范顾问

面对新场景时：

1. 先说明当前规则如何处理
2. 再单独给出调整建议

**现行规范与建议不得混写。**

规范维护者无权自行修改正式规范。

---

# 29. 每周规范蒸馏

每周整理：

- 本周新增问题
- 重复出现的问题
- 高影响单次问题
- 长期持续问题
- 建议修改项
- 待归档项

需要修改规范时，与用户讨论后决定。

只有用户确认后才能：

- 修改正式规范
- 建立必要 Decision Record
- 升级规范版本

---

# 30. 流程问题归档

某问题：

- 两个月内只出现一次
- 影响较低
- 没有再次发生

可以归档。

归档不等于删除。

后续再次出现时重新激活。

以下问题即使只出现一次，也不得因为低频自动归档：

- 数据丢失
- 安全问题
- 权限问题
- 严重交接失败
- 其他高影响问题

---

# 31. 敏感信息

禁止将以下内容直接写入 Git：

- API Key
- 密码
- Token
- Cookie
- 私钥
- 其他真实凭据

项目可以记录：

- 需要什么凭据
- 应配置在哪里
- 配置方式

但不能保存凭据本身。

提交前必须检查是否误提交敏感信息。

---

# 32. 大文件和外部资料

Git 不强制保存所有项目文件。

以下内容可放外部存储：

- 视频
- 大型素材
- 数据集
- 大型设计文件
- 其他不适合版本仓库的文件

项目中记录：

- 存放位置
- 用途
- 对应版本或关联任务
- 必要时记录校验信息

避免为了“全部进入 Git”而导致仓库失控。

---

# 33. 平台迁移

当前任务管理和 PR 可以使用现有 Git 协作平台。

但项目不能把关键历史只理解为 Git 文件本身。

如果未来迁移平台，必须同步迁移或归档：

- Issue
- PR
- 标签
- 任务状态
- Decision Record 关联
- 必要的评论和交接记录

不能只迁移 Git 仓库而丢失协作历史。

---

# 34. 推荐项目结构

项目初始只创建真正需要的文件。

基础：

```text
README.md
PROJECT.md
AGENTS.md
```

需要重要决策时再创建：

```text
docs/
  decisions/
```

其他目录：

```text
docs/research/
docs/handoff/
docs/architecture/
docs/testing/
docs/deployment/
deliverables/
```

都按实际需要创建。

禁止为了“结构完整”提前建立大量空目录和空文档。

---

# 35. Idea Lab 推荐结构

```text
README.md
AGENTS.md

ideas/
  inbox/
  exploring/
  validating/
  ready/
  parked/
  dropped/

templates/
  idea.md
```

每个 Idea 使用独立 Markdown 文件。

---

# 36. V1 明确暂不做的事情

V1 不提前实现：

- 自动项目初始化脚本
- 自动跨模型额度切换
- 复杂风险评分系统
- 复杂模型性能评分系统
- 自动批量升级所有旧项目
- 大量固定目录
- 过度复杂的 Issue 标签
- 未经过真实项目验证的自动化流程

这些能力只有在实际使用证明有需求后再增加。

---

# 37. 总体工作链路

## 想法

`捕获 → 探路 → 验证 → Ready`

## 项目

`立项 → 规划 → 执行 ↔ 验证 → 阶段交付 → 维护 / 迭代`

## 标准任务

`Issue → Branch → 执行 → 验证 → PR → 必要的独立审查 → 用户确认 → main`

## 规范优化

`问题出现 → 沉积 → 每周蒸馏 → 建议 → 用户确认 → 修改规范 → 新版本`

整个系统的目标不是让所有工作流程变复杂，而是做到：

**任何项目在更换人员、AI、模型、账号、电脑或执行环境后，都能够清楚知道项目是什么、当前做到哪里、为什么这样决定，以及下一步应该做什么。**
