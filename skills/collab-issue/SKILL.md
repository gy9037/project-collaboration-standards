# Issue 新建与补全

## 用途

让每个需要追踪的工作有一个可执行、可验收的 Issue（规范第 3 条）：执行者看了就能开工，验收者看了就能逐条核对。

## 触发场景

- 用户提出新需求、报告问题、要求调研或维护。
- 执行中发现超出当前 Issue 范围的独立需求。
- 大任务需要拆分。
- collab-assignment 判定「需补全」，或现有 Issue 缺字段、缺标签。

不触发：

- 极小改动（见第 1 步）：直接走分支和 PR，PR 里写免 Issue 的依据。
- 还没立项的想法 → collab-idea。

## 步骤

1. **判断规模**（拿不准按标准任务）：

   | 规模 | 特征 | 处理 |
   |---|---|---|
   | 小改动 | 单点、低风险、一次完成、无需独立验收、不涉及他人 | 不建 Issue，仍走分支和 PR（规范第 4 条） |
   | 标准任务 | 有明确目标和验收标准，改正式内容，需要追踪或可能交接 | 建 1 个 Issue |
   | 大型任务 | 多模块、多人或多 Agent、多个独立验收单元、依赖复杂、周期长 | 建主 Issue + 子 Issue（第 4 步） |

2. **查重。** `gh issue list --state all --search "<关键词>"`。已有同目标 Issue 时补全它，不新建。
3. **选类型，套模板。** 模板在 `.github/ISSUE_TEMPLATE/`（来源：规范仓库 `project-template/.github/ISSUE_TEMPLATE/`）。每个 Issue 都要有：目标或问题、验收标准、关联对象、当前状态、负责人 / 依赖 / 下一步。类型字段：

   | 类型 | 何时用 | 必填扩展字段 |
   |---|---|---|
   | feature | 新增能力 | 背景、范围、暂不做、依赖 |
   | bug | 已有行为与预期不符 | 现象、复现步骤、预期结果、实际结果、环境 |
   | improvement | 已有能力变好 | 当前问题、优化目标、约束 |
   | research | 产出是结论而非改动 | 要回答的问题、调研范围、输出物、结束条件 |
   | maintenance | 依赖、配置、迁移、清理 | 修改内容、风险、验证方式 |

   一个 Issue 只选一个类型；跨类型就拆。
4. **大型任务拆分。** 主 Issue 写总目标、子 Issue 列表（`- [ ] #N`）和依赖顺序。每个子 Issue 独立可验收、能在一个短期分支内完成，正文写 `Parent: #主Issue`，有依赖写 `Depends on: #N`。
5. **写验收标准。** 每条满足：
   - 能判断是否做到（给出命令、路径、数值、可观察的结果），不写「体验更好」「优化性能」。
   - 写清用什么方法验证（运行什么、核对什么来源）。
   - 涉及 Critical Area 的，写明要跑的回归验证。
   - 需要用户取舍才能定的标准，在 Issue 中列出问题和选项，标注「待用户决定」，不自行替用户定。
6. **标签和状态。** 打 1 个类型标签 + 1 个状态标签：

   | 状态 | 含义 | 谁改 |
   |---|---|---|
   | todo | 可排期，未开工 | 新建时 |
   | in-progress | 有负责人在做 | collab-assignment 分配时 |
   | blocked | 等依赖或外部条件，正文写等什么 | 发现阻塞时 |
   | review | 已交付，待验收 | 执行者交付时 |

   同一时间只保留一个状态标签。完成即关闭（Closed），不建 done 标签。其他标签真用得到时再加。
   ```sh
   gh issue create --title "<动词开头的目标>" --label feature,todo --body-file <正文文件>
   gh issue edit <N> --remove-label todo --add-label in-progress
   ```
7. **范围扩张。** 执行中发现新的独立需求：回到第 1 步另建 Issue，在原 Issue 记一条「拆出 #N」，不扩大原 Issue。
8. **自检。** 对照下方「验收」逐条检查。

## 示例

用户：「导出报表时选的日期范围不生效，导出的总是全部数据。」

1. 规模：标准任务。查重无结果。
2. 类型 bug，套 `bug.md`：
   - 目标：导出报表按所选日期范围过滤。
   - 复现：选 2026-11-01 至 2026-11-07 → 点导出 → 打开文件。预期：只含该区间数据。实际：包含全部数据。环境：生产版本 v1.4，Chrome。
   - 验收标准：
     - [ ] 新增测试：给定 3 个日期的数据、筛选其中 1 天，导出只含该天的行（`pytest tests/test_export.py` 通过）。
     - [ ] 不选日期时导出全部数据，行为不变（原有测试通过）。
3. 标签 `bug`、`todo`，交给 collab-assignment。

## 验收

- [ ] 规模判断有依据；小改动没建 Issue 但 PR 写了依据。
- [ ] 没有与已有 Issue 重复。
- [ ] 通用字段齐全，所选类型的扩展字段全部填写。
- [ ] 每条验收标准可逐条判断，写了验证方法；待用户取舍的已标注。
- [ ] 恰好 1 个类型标签和 1 个状态标签。
- [ ] 大型任务的子 Issue 各自可验收，互相标了 Parent / Depends on。
