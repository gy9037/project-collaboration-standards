# 规范维护

## 用途

落实规范第 9 条。让流程问题先沉淀为记录，再由维护者整理成有证据的修改建议，经用户确认后进入新版本或新 skill。

## 触发场景

- 任何项目中发现流程问题（规则缺失、矛盾、难执行、执行后仍出错）→ A；
- 到了整理周期（默认每周），或待整理反馈已积累 → B；
- 用户或 Agent 问「某条规则现在怎么执行」「这个新场景该怎么办」→ C；
- 要修改正式规范或规范仓库 `skills/` 下的 skill → D；
- 新版本已发布，要判断各项目是否升级 → E。

不触发：

- 项目自身的 bug 或需求，走该项目的 Issue；
- 项目锁定版本内已有明确答案、执行者只是没读到，直接按规则做。

## 步骤

### A. 记录流程反馈

1. 先记录，不改规范，也不判断是否值得改规范。
2. 在规范仓库新建 `standards/feedback/YYYY-MM-DD-<主题>.md`，按 `optional-templates/feedback.md` 填写，至少有：问题、影响、出现的场景、日期；附关联项目 / Issue / 证据链接，状态写「待整理」。
3. 同一问题已有记录：不新建，在原记录「再次出现记录」追加日期和证据；原记录已归档的改回「待整理」。
4. 经分支和 PR 提交，按 collab-merge 判档。只新增或追加反馈、不改规则的 PR，满足第一档条件时由 AI 合并并通知。

### B. 定期整理

1. 读取 `standards/feedback/` 中状态为「待整理」的记录。
2. 按 `optional-templates/weekly-distillation.md` 分六类整理：本周新增、重复出现、高影响单次、长期持续、建议修改、待归档。
3. 归档判断：
   - 可归档：两个月内只出现一次、影响低、此后未再发生。状态改为「已归档」，写明原因和日期，文件保留不删。
   - 不因低频归档：数据丢失、安全、权限、严重交接失败及其他高影响问题。
4. 「建议修改」逐条写：现行规则原文位置、问题证据、修改建议、影响哪些项目。
5. 整理结果发在规范仓库一个 Issue 中交用户。有建议修改的，用户决定后进入 D。

### C. 回答规则问题

1. 先确认提问项目 AGENTS.md 锁定的版本和 Overrides，按该版本回答，不按最新版本回答。
2. 回答分两段，不混写：
   - **现行规则**：引用版本和条款号（或 skill 名和步骤），说明现在怎么做；规则没有覆盖时直接写「现行规则未覆盖」。
   - **建议**（可选）：单列，标明「建议，未生效」。
3. 建议涉及规则缺口时，同时按 A 记录反馈。

### D. 修改规范或 skill

1. 在规范仓库建 Issue，写明要改什么、依据哪些反馈或证据、与现行版本的差异。
2. 建任务分支修改：
   - 正式规范：新建 `standards/versions/vX.Y/` 目录，已发布版本目录不改动；
   - skill：直接修改 `skills/<name>/SKILL.md`（正本）；
   - 需要记录原因的，按 collab-decision 新建 DR。
3. 开 PR。修改正式规范、发布新版本（规范第 9 条），或改变 skill 的步骤、判定条件，按规范第 5 条第二档，用户确认后合并。只改 skill 措辞、不改变执行方式的，按 collab-merge 判档。
4. 合并后：
   - 新版本：更新 `standards/README.md` 当前版本入口，然后进入 E；
   - skill：同步安装到各工具。把 `skills/<name>` 目录链接或复制到所用工具的 skill 目录，例如 `~/.config/opencode/skills/`、`~/.claude/skills/`、`~/.agents/skills/`。复制安装的，每次合并后重新复制；安装后打开目标目录核对文件与 main 一致。
5. 将相关反馈状态改为「已处理」，写明对应 PR。

### E. 新版本发布后评估项目

1. 列出所有使用本规范的项目及其锁定版本。
2. 对每个项目按差异给出结论之一，写明理由：
   - 无需处理：差异不影响该项目；
   - 建议升级：新版本更好，但旧版本继续执行没有风险；
   - 必须升级：旧版本会导致数据丢失、安全、权限问题或与平台现状冲突。
3. 评估结果发在规范仓库 Issue 中交用户。不直接修改任何项目。
4. 用户确认某项目升级后，在该项目中按 collab-project-setup 的升级步骤执行。

## 示例

某项目执行者反馈：「合并后 PROJECT.md 仍写着等待确认」。

1. A：新建 `standards/feedback/2026-11-20-合并后状态未同步.md`，填写问题、影响（接手者误判阶段）、场景、日期，状态「待整理」，经 PR 合并。
2. 一周后又发生一次：在原记录追加再次出现记录。
3. B：整理时归入「重复出现」和「建议修改」，建议在 collab-merge 收尾步骤加「对照 PROJECT.md 检查阶段描述」，发 Issue 交用户。
4. 用户同意。D：建 Issue 和分支，只改 `skills/collab-merge/SKILL.md`，新增了步骤，属第二档，用户在 PR 中确认后合并，合并后把该目录重新复制到各工具 skill 目录，反馈改为「已处理」。

## 验收

- [ ] 每条流程反馈有问题、影响、场景、日期，存于 `standards/feedback/`；重复问题追加而非新建
- [ ] 整理结果覆盖六类；归档项满足条件，高影响问题未因低频归档；归档文件未删除
- [ ] 规则问题的回答按锁定版本，现行规则与建议分段，建议标明未生效
- [ ] 正式规范修改在新版本目录，旧版本未改动，PR 中有用户确认
- [ ] skill 修改走了 Issue → 分支 → PR，合并后各工具已同步安装并核对
- [ ] 新版本发布后每个项目都有「无需处理 / 建议升级 / 必须升级」结论，未擅自修改项目
