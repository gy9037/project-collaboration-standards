# 制作自动化

## 用途

把重复工作安全地交给自动化：只自动化有手动记录、有可度量成功标准、在建议模式下达标的决定点；转自动后随时能关、能退、能查。

## 触发场景

- 用户要求「以后这个自动做」；
- 某项手动操作反复出现，AI 打算提议自动化；
- 已有自动化要扩大范围（覆盖新的决定点或新项目）。

不触发：

- 一次性脚本，只跑一次、不替人做判断；
- 执行会话内的普通工具调用（读写文件、运行测试）。

## 硬约束

- 自动化不得绕过规范第 5 条（合并分档）和第 6 条（用户审批清单）。第 6 条事项永远停在「建议」，由用户审批。
- 同一自动化对所有项目使用同一规则，代码和配置中不出现针对个别项目的分支。确需例外时，写进该项目 AGENTS.md 的 Overrides，自动化读取 Overrides 执行。

## 步骤

1. **确认需求和决定点。** 在 Issue 中写清：
   - 要自动化的具体决定点（自动化替人做的那个判断，例如「这个 Issue 能否开工」「这个 PR 是否属于第一档」）；
   - 输入、输出、作用范围（哪些项目）；
   - 是否触及第 5、6 条。触及第 6 条的部分划出范围，只做建议。
2. **找手动运行记录。** 在 Issue / PR / 日志中找该决定点过去人工处理的记录。
   - 决策点：没有记录，或记录不足以看出人工如何判断 → 先手动执行，每次在 Issue 中记录输入、判断、结果，攒够记录再继续。
3. **定成功标准。** 标准必须可度量，例如「连续 N 次建议用户未改动，且无执行错误」。N 及其他阈值由用户确定，写入 Issue。
4. **建议模式运行。** 自动化只产出建议，由用户或指定的人执行。每次运行记录：时间、输入、建议、用户是否改动、改动内容、是否出错。记录存放位置在 Issue 中写明（Issue 评论或仓库内日志文件）。
   - 决策点：用户改动了建议 → 计数清零，分析原因，修正规则后继续建议模式。
5. **达标后转自动。** 记录显示满足第 3 步标准时，在 Issue 中列出达标证据（记录链接、次数、改动次数、错误次数），请用户同意。用户同意后才开启自动执行，同意记录留在 Issue 中。
6. **上线必备三项，缺一项不开启：**
   - 开关：一处配置即可关闭，写明位置；
   - 回退方式：关闭后如何回到建议模式或手动，自动执行产生的结果如何撤销；
   - 执行记录：每次自动执行写入记录（时间、输入、动作、结果），位置固定、可查。
   三项写入该自动化的说明文档或所在项目的 PROJECT.md 重要入口。
7. **出错时退回。** 自动执行出错，或结果被用户撤销时：立即切回建议模式，在 Issue 中记录错误和证据，修正后从第 4 步重新计数。

## 示例

想把「Issue 是否可以开工」自动判断并分配执行者。

1. 决定点：「Issue 有目标、验收标准，且无未解决依赖时，标记为可开工并分配」。不涉及第 6 条；分配后的合并仍按第 5 条。
2. 过去两周有 12 次人工分配记录在各 Issue 评论中，记录够用。
3. 用户定标准：连续 10 次建议未被改动且无错误。
4. 建议模式：自动化在 Issue 评论建议「可开工，分配给执行者 X」，用户执行。第 6 次用户改了执行者 → 计数清零，修正路由规则，再跑 10 次全部未改动。
5. 在 Issue 列出 10 次记录链接，用户同意转自动。
6. 开关为配置项 `auto_assign: true`；回退为改 `false` 并手动撤销本次分配；执行记录写入固定日志文件。
7. 某次把已关闭 Issue 标为可开工 → 切回建议模式，修复后重新计数。

## 验收

- [ ] Issue 中写明决定点、范围，以及与第 5、6 条的关系
- [ ] 有手动运行记录；没有时先手动执行并记录
- [ ] 成功标准可度量，阈值由用户确定
- [ ] 建议模式每次运行都记录了用户是否改动
- [ ] 转自动前有达标证据和用户同意记录
- [ ] 开关、回退方式、执行记录三项齐全且位置已写明
- [ ] 第 6 条事项仍由用户审批；规则对所有项目一致，例外只写在 Overrides
- [ ] 出错后已退回建议模式并重新计数
