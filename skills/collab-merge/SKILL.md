# 合并

## 用途

把已验收的任务分支经 PR 安全合入 main：判定档位，第一档自行合并并留痕，第二档取得用户确认后合并，出问题时可回退。

## 触发场景

- 任务分支要 commit、push 或开 PR。
- collab-verification 结论为通过或部分验证，PR 待合并。
- 第二档确认卡超过 24 小时未处理。
- 已合并的修改需要回退。

不触发：验收结论为不通过，此时按 collab-verification 退回执行者。

## 步骤

### A. commit 与 PR

1. 每个 commit 只含一类修改，不混入其他任务。信息用 `<类型>: <说明> (#Issue)`，类型取 feat / fix / docs / refactor / test / chore / build。
2. 提交前运行 `git status` 与 `git diff --staged`，确认没有：凭据（Key、Token、密码、Cookie、私钥）、日志、临时文件、无关大文件、其他任务的改动。发现即移出暂存区，凭据已进历史时停止并告知用户。
3. 分支名 `<类型>/<Issue号>-<短名>`，类型取 feat / fix / docs / refactor / chore；强相关的极小任务可共用一个分支。只 push 任务分支；不 push main，不 `--force` 共享分支。
4. PR 描述按 project-template/.github/pull_request_template.md 填写：对应 Issue、实际完成内容、验证方法与结果、风险/未解决项/未验证内容、是否偏离计划、独立审查、合并档位（第 5 步的判定和依据）。没有的项写「无」，不留空。

### B. 判定档位

5. 逐项核对规范第 5 条第一档的 5 个条件，每项写出依据：
   1. 不涉及 Critical Areas：`gh pr diff --name-only` 对照 PROJECT.md 登记的 Critical Areas。改动 AGENTS.md、PROJECT.md 的 Critical Areas 段、`.standards/`、main 拦截配置（hook、执行端权限）、已安装 skill 的，一律第二档。PROJECT.md 写「待识别」且改动涉及核心功能、数据、配置、依赖清单/锁文件、构建与部署配置时，按涉及处理。
   2. 无等待用户取舍的决定：Issue、PR 中没有未答复的用户问题。
   3. 每条验收标准有证据，且验收者不是执行者：查 PR 中的验收结果。需要独立审查的，审查结论无未解决问题，修订已复核；否则按不满足处理。
   4. 无未验证项：验收结论为「通过」，未验证内容为「无」。
   5. 合并本身不触发规范第 6 条事项：按合并后的 CI/CD 配置判断 main 合并是否会自动部署、发布、对外发送、产生费用或改权限；PR 新增或修改 CI/CD、部署、发布、定时任务、Secrets 引用的，一律第二档。
6. 五项全满足 → 第一档（C）；任一不满足或拿不准 → 第二档（D）。

### C. 第一档：自行合并

7. 同步最新 main 到任务分支（`git fetch origin` 后 `git merge origin/main`；已推送的分支不 rebase，否则需要强推，会被 main 拦截 hook 拒绝），解决冲突。
8. 重跑验证入口，`gh pr checks <PR>` 全部通过（没有检查时在 PR 写明「无 CI 检查」）。冲突解决改动了验收涉及的内容时，回到 collab-verification 复验，再从第 5 步重新判定。
9. `gh pr merge <PR> --squash --delete-branch`。
10. PR 评论：

    ```
    自动合并（第一档）
    1 Critical Areas：未涉及，改动文件 <…>
    2 用户取舍：无
    3 验收：<验收结果链接>，验收者 <…>
    4 未验证项：无
    5 第 6 条事项：按合并后配置，main 合并不触发部署/发布；未新增或修改 CI/CD、部署、发布、定时任务、Secrets 引用
    检查：gh pr checks 全部通过（或：无 CI 检查）
    合并提交：<sha>
    ```

11. 通知用户（发到 AGENTS.md 登记的通知渠道）：「已合并 #PR：<一句话内容>。回退：revert <sha> 并走 PR。」关闭 Issue。检查 PROJECT.md 的阶段和当前重点是否需要更新；阶段验收完成时更新阶段（改 PROJECT.md 另走 PR）。

### D. 第二档：用户确认

12. 按 optional-templates/merge-confirmation.md 生成确认卡，并写明「第二档，原因：条件 N 不满足（依据）」。
13. 送达：发到 AGENTS.md 登记的用户固定会看的通知渠道（如工作台待确认列表、项目协作群）；同时在 PR 评论保存一份。AGENTS.md 未登记渠道时，发到当前会话并提醒用户补登记。
14. 用户回复后，在 PR 评论记录：用户原话或消息链接、日期、对应 commit、选择。
    - 合并：执行第 7–9 步。同步 main 或之后出现影响验收或风险的新提交时，更新确认卡重新确认；不影响时在 PR 注明理由后合并。合并后按第 11 步通知并关闭 Issue。
    - 要求修改：Issue 改回 `in-progress`，交原执行者，修改后重新验收和确认。
    - 暂不合并：PR 保持开放，Issue 记录原因，不再提醒。
15. 未处理提醒：卡片发出超过 24 小时无回复，在同一渠道提醒一次；之后只在通知渠道的下一次汇报中列出（没有登记渠道时在下一次对话开头列出），不再单独发送。

### E. 回退

16. 从最新 main 建分支 `revert/<PR号>`，`git revert <合并提交sha>`，开 PR 说明回退原因并关联原 Issue。回退 PR 同样按 B 判定档位，不直接推送 main。

## 示例

PR #51（Issue #42）验收结论「部分验证」，跨年区间未验证。

- 第 5 步：条件 1、2、3、5 满足，条件 4 不满足 → 第二档。
- 生成确认卡：做了什么「导出报表增加日期筛选」；验收 3 条中 3 条通过；未验证「跨年区间」；风险「跨年数据可能漏行」；回退「revert 合并提交并走 PR」；AI 建议「建议合并，跨年场景当前无用户使用」。
- 发到项目协作群，PR 评论存一份。次日用户未回复，群内提醒一次。
- 用户回复「合并」。PR 评论记录：「用户原话：合并；2026-11-26；commit a1b2c3d」。同步 main 无冲突，测试通过，squash merge，群内通知并关闭 Issue。

## 验收

- [ ] 提交前检查过 diff，无凭据、日志、临时文件、无关文件。
- [ ] PR 描述各节已填写，空项写「无」。
- [ ] PR 中有档位判定，5 个条件各有依据。
- [ ] 合并前 `gh pr checks` 全部通过，或 PR 写明无 CI 检查。
- [ ] 第一档：合并前同步 main 并重跑验证；PR 有「自动合并（第一档）」评论；用户收到含回退方式的通知。
- [ ] 第二档：确认卡同时在通知渠道和 PR 中；PR 记录了用户原话和对应 commit；确认后的影响验收的提交已重新确认。
- [ ] 提醒最多单独发一次，之后只出现在下一次汇报或下一次对话开头。
- [ ] 合并方式为 squash，任务分支已删除，Issue 已关闭；已检查 PROJECT.md 阶段和当前重点。
