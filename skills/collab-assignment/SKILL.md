# 安排执行者

## 用途

由协调者判定 Issue 能否开工，给能开工的 Issue 选定一个主要负责人，并避免并行任务互相冲突。所有项目使用同一套规则。

## 触发场景

- 新 Issue 需要安排执行者。
- 同时推进多个 Issue，需要判断能否并行。
- 执行者中途退出、验收退回或交接后需要重新安排。
- 协调者定期扫描开放 Issue（自动分配模式）。

不触发：

- 不需要建 Issue 的极小修改（规范第 3 条），直接执行。
- Issue 内容本身不完整到无法判断目标：先用 collab-issue 补全。
- 已分配且正在执行的 Issue，只需交接时用 collab-handoff。

## 步骤

1. **读取现状**。读 PROJECT.md（Critical Areas、当前重点）、AGENTS.md（默认路由、通知渠道）、目标 Issue，以及所有 in-progress 的 Issue 和开放 PR。
2. **逐项核对「可开工」清单**：
   - [ ] A. 有目标和验收标准，验收标准可逐条验证。
   - [ ] B. 依赖的 Issue 全部已关闭。
   - [ ] C. 没有等待用户取舍的问题。
   - [ ] D. 没有其他负责人，没有关联该 Issue 的进行中分支或开放 PR（查 Issue 记录、`git branch -r`、`gh pr list`）。
   - [ ] E. 预计修改范围与进行中的任务不重叠：修改同一文件或同一 Critical Area 即视为重叠（对比对方 Issue 记录的范围和 PR 的 `gh pr diff --name-only`）。
3. **得出结果**（决策点）：
   - B、D、E 任一不满足：本轮不分配。B 不满足打 `blocked` 并写明等待哪个 Issue；D 不满足跳过；E 不满足保持 `todo` 并写「等待 #N 合并后开工」。
   - 五项全满足 → **可直接分配**，进入第 4 步。
   - 仅 A 不满足，或缺类型标签 → **需补全**：协调者按 collab-issue 补验收标准和标签，补完回到第 2 步重新判定。补验收标准需要用户取舍时，转为「需用户决定」。
   - C 不满足 → **需用户决定**：把待定事项整理成一个问题，附 2–3 个选项和 AI 建议，发到 AGENTS.md 登记的通知渠道，并在 Issue 记一份。用户回复后把原话记入 Issue，回到第 2 步。
4. **选择执行者**，按以下依据：任务类型、复杂度、能力匹配、所需工具条件、可用额度和成本、任务连续性。
   - 曾有执行者的 Issue（验收退回、暂停后恢复、交接后继续）优先给原执行者。
   - 简单和标准任务协调者可自己执行；复杂、跨模块或高风险任务优先交给执行者。协调者自己执行时，验收必须另找他人（规范第 5 条第一档条件 3）。
   - AGENTS.md 或工作台登记了默认路由时按默认执行；偏离默认时在 Issue 写明原因。
5. **记录分配**。在 Issue 评论写分配记录（格式见示例），打 `in-progress` 并移除 `todo`。同一 Issue 同时只有一个主要负责人；换人时先由原负责人或协调者按 collab-handoff 写交接，再改记录。
6. **并行冲突控制**：
   - 同时开工的任务，两两核对依赖、预计修改范围、是否涉及同一 Critical Area。
   - 修改同一文件或同一 Critical Area 即视为重叠；重叠的任务顺序执行，不并行。
   - 涉及同一 Critical Area 的任务不并行；只涉及不同 Critical Area 的任务可以并行，但都按第二档合并（规范第 5 条）。
   - 执行中发现实际修改范围超出分配记录，执行者在 Issue 更新范围，协调者重新做第 6 步核对。
   - 合并前同步最新 main、冲突解决后重新验证，按 collab-merge 执行。
7. **自动分配模式**：
   - 协调者在每次协调会话开始时，以及工作台或定时任务触发时，扫描所有开放且未分配的 Issue，不分项目，统一按第 2–6 步判定。
   - 「可直接分配」的直接分配；「需补全」的当轮补全后再判定一次；「需用户决定」的同一问题只发一次，之后在通知渠道的下一次汇报中列出（没有登记渠道时在下一次对话开头列出），不重复发送。
   - 每轮扫描结束，在协调记录（工作台或协调 Issue）写一行汇总：分配了哪些、跳过哪些及原因、等用户决定哪些。

## 示例

扫描到 Issue #42「导出报表增加日期筛选」，标签 `feature`、`todo`。

- A：有目标，验收标准 3 条，可验证 ✔；B：依赖 #38 已关闭 ✔；C：无待定 ✔；D：无负责人、无关联分支和 PR ✔。
- E：#40 正在改 `src/report/query.ts`，#42 预计也改该文件 → 不满足。保持 `todo`，评论「等待 #40 合并后开工」。
- 下一轮 #40 已合并，重新判定五项全满足。#42 曾无执行者；任务为单模块标准 feature，默认路由为代码执行 Agent，额度充足。

Issue #42 评论：

```
分配：代码执行 Agent（会话 <id>）
依据：标准 feature，单模块；工具条件满足；额度充足
偏离默认路由：无
预计修改范围：src/report/、tests/report/；不涉及 Critical Areas
并行核对：与进行中的 #43（docs/）无重叠
```

随后打 `in-progress`。

## 验收

- [ ] 每个被处理的 Issue 都有明确结果：已分配 / 需补全后已重判 / 已发用户问题 / 本轮不分配及原因。
- [ ] 已分配的 Issue 有分配记录（执行者、依据、偏离原因、预计范围、并行核对），标签为 `in-progress`，只有一个主要负责人。
- [ ] 同时进行的任务之间没有修改同一文件，没有同时修改同一 Critical Area。
- [ ] 发给用户的问题每个 Issue 只有一个，带选项和建议，未重复发送。
- [ ] 协调者自己执行的 Issue 已注明验收需由他人完成。
