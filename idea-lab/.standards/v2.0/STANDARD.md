# 项目协作规范

版本：V2.0
状态：正式规范

本规范只写原则和底线。具体怎么做由 skill 承担，什么场景用哪个 skill 见第 10 条触发表。目标是：任何项目在更换人员、AI、模型或电脑后，都能知道项目是什么、做到哪里、为什么这样决定、下一步做什么。

---

## 1. 事实源

聊天记录只作参考，不是事实源。各类信息以下列位置为准：

| 信息 | 事实源 |
|---|---|
| 执行规则 | AGENTS.md |
| 项目当前状态 | PROJECT.md |
| 任务状态、交接 | Issue / PR |
| 重要决定的原因 | Decision Record |
| 实际成果 | 代码、测试结果、正式交付物 |

不同事实源互相矛盾时，按证据判断：能确认的同步修正，不能确认的交用户判断。不得直接用一个覆盖另一个。

## 2. 项目核心文件

每个正式项目至少有三个文件：

- README.md：项目是什么、怎么开始了解或使用。
- PROJECT.md：目标、类型、当前阶段、当前重点、关键约束、Critical Areas、重要入口。只在这些内容变化时更新，不写流水账。
- AGENTS.md：规范源仓库和锁定的版本、开工前要读什么、验证入口、通知用户的渠道、项目特殊规则（Overrides）。

Critical Areas 指损坏、丢失或误改后难以恢复，或影响项目主要目标的部分。在 PROJECT.md 中逐步登记；拿不准是否属于时按属于处理。

## 3. Issue

需要追踪的工作建 Issue，至少写明目标和验收标准。极小、低风险、一次即可完成的修改可以不建 Issue，但仍走第 4 条。

## 4. 进入 main 的路径

- 所有修改从任务分支经 PR 进入 main，不直接推送或强推 main。
- 一个 Issue 对应一个短期分支，合并后删除。
- 合并前同步最新 main；解决冲突后重新验证。
- 默认 Squash Merge。

## 5. 合并

PR 分两档：

**第一档：AI 自行合并，合并后通知用户。** 同时满足：

1. 不涉及 Critical Areas（含未登记但拿不准的，按涉及处理）；
2. 不包含等待用户取舍的决定；
3. 每条验收标准都有证据，并经执行者以外的验收者核对；需要独立审查的已完成审查；
4. 没有未验证项；
5. 合并本身不会触发第 6 条中的事项（例如合并即部署或发布）。

**第二档：用户确认后合并。** 其余所有 PR。确认时向用户提供：做了什么、验收结果、未验证内容、风险、回退方式、AI 建议。

两档都在 PR 中记录合并档位和依据。

## 6. 必须由用户审批的事项

只有下列事项需要用户审批：

1. **生产部署和对外发布或发送。** 对外指：发给项目以外的人（客户、终端用户、合作方等）、公开发布内容、以用户个人名义对外沟通。项目群内与 Agent、协作者的沟通不算对外。
2. **不可恢复的删除。** 能从 Git 历史或备份恢复的不算。
3. **账号、密钥和平台权限的变更。** 执行会话内的读写文件、运行命令等工具权限不算。
4. **产生实际费用。**

合并按第 5 条处理，不在本清单中。清单以外的事 AI 自行处理，在对应 Issue / PR 中留下记录并汇报，不因等待审批停工。任何自动化都不得绕过本条和第 5 条。

## 7. 敏感信息

API Key、密码、Token、Cookie、私钥等凭据不得写入 Git。可以记录需要什么凭据、配置在哪里，不能记录凭据本身。提交前检查 diff。

## 8. 可恢复

- 每完成一个经过验证的阶段就 commit，重要进度及时 push 到远端任务分支，不长期只留在本地。
- 换执行者、换模型、暂停或额度将尽时，在当前 Issue 写清进度和下一步。
- 接手者按 PROJECT.md → AGENTS.md → 当前 Issue → 当前 PR → 分支与 commit 的顺序恢复，不依赖旧聊天记录。

## 9. 规范版本

- 项目执行自己 AGENTS.md 中锁定的版本，中央规范升级不自动改变旧项目。
- 发布新版本、修改正式规范需用户确认；已发布版本保留不覆盖。
- 修改 skill 的步骤或判定条件，等同修改规范，按第 5 条第二档合并；只改措辞的按第 5 条正常判档。
- 项目升级前说明差异和风险，经用户确认后执行。

## 10. 触发表

遇到下列场景时，使用对应 skill（正本在规范仓库 `skills/`）：

| 场景 | skill |
|---|---|
| 有新想法、判断是否值得立项 | collab-idea |
| 新建项目、把已有仓库接入本规范、项目升级规范版本、迁移平台 | collab-project-setup |
| 新建或补全 Issue | collab-issue |
| 安排执行者、并行推进多个 Issue | collab-assignment |
| 任务交付后验收 | collab-verification |
| PR 准备合并 | collab-merge |
| 换执行者、换模型、暂停、额度将尽，或接手进行中的任务 | collab-handoff |
| 做出影响未来判断的决定 | collab-decision |
| 发现流程问题、整理反馈、修改规范或 skill、发布新版本 | collab-standard-maintenance |
| 要把某项工作做成自动化 | collab-automation |

开始任务前对照本表；场景匹配时先读对应 skill 再执行。skill 与本规范冲突时以本规范为准。
