## 开始与恢复

1. 读 PROJECT.md、此文件、当前 Issue、当前 PR，再检查相关 commit 和分支状态。
2. 首次接手读锁定规范；后续按本文件的场景指引查阅对应章节。
3. 对照证据处理分类事实源失配；可确认则同步，无法确认交用户判断。聊天只是参考。
4. 进入执行前检查可验收阶段目标、范围、约束、依赖验证或计划、阻塞负责人及首批任务。

## 执行

需要追踪的工作建 Issue；不明确时按标准任务处理。默认一个 Issue 一个短期分支，任务分支执行、验证、提交、push、PR；main 只接收经用户确认的 PR。极小低风险一次性改动可免 Issue，仍走分支与 PR。

验证按 PROJECT.md 的实际入口及验收标准进行。每个可验证单元验证，失败返回执行；明确记录未验证内容。涉及关键区域、不确定风险、验证不足或用户要求时，读规范第 18～19 节并安排独立审查。

并行前检查依赖与修改范围，同一 Issue 只有一个主要负责人；重叠任务优先顺序执行。合并前同步最新 main，解决冲突后重新验证。

提交前检查 diff、敏感信息及无关文件；已验证阶段及时 commit，重要恢复点 push。PR 用模板记录结果和风险，最终给用户合并确认卡；批准后才合并当前经审查版本，默认 Squash Merge。

## 权限与交接

可自行读文件、管理 Issue、建分支、修改、测试、commit、push 任务分支、创建 PR 和维护项目文档。

合并 main、生产部署、重要删除、账号/密钥/权限修改、重大依赖升级、实际费用、对外正式发布或发送，需要用户确认。按规范第 20 节执行。

切换执行者、模型、暂停或额度临近限制时在当前 Issue 写进度、完成/未完成、关键改动、风险、下一步、commit/PR。复杂交接才按需建立 docs/handoff。

重要决定按第 24 节建立 DR；反馈和规范升级按第 25～30 节处理；外部资料及平台迁移按第 31～33 节处理。升级评估差异和风险后由用户确认，保留历史版本。
